# Windows 播放性能修正与比赛要求差距

## 1. 本轮结论

没有重新训练模型，也没有使用本机 BDD100K 开始训练。当前车道分割用官方 YOLOP 在 **BDD100K** 上训练好的权重；不是 BDD300K。预训练模型仍不能直接输出虚实线类别。

旧版串行执行 YOLOv5 与 YOLOP 的 CPU 推理，并让视频播放等待整个分析完成。其约 390～410 ms/帧只能提供约 2.5 次分析/秒，不适合作为题目要求的实时演示；Windows 规则原型也不能说明板端实时部署已完成。

本轮修正运行后端与播放调度，没有重训模型、降低模型输入分辨率或改变主要行为规则。电脑存在 RTX 4060，DXGI 适配器 0 已核对为该 GPU；现在通过 ONNX Runtime DirectML 使用它，不需要 CUDA 版 PyTorch。

## 2. 启动与界面

```powershell
cd 'F:\B_file\jichuangsai\Pango_FPGA\09_pcie_test\pcie_host'
.\run_video_decision.cmd 'D:\buduinetdiskdownload\video_20260929_112507.mp4'
```

| 模式/参数 | 行为 |
| --- | --- |
| 默认窗口 / `--playback realtime` | 视频按源时间原速播放；后台独立分析，待处理队列只保留最新一帧 |
| `--backend auto` | 优先 DirectML GPU；初始化或预热失败时提示并回退 CPU |
| `--backend directml` | 强制 GPU，失败就报告错误，避免误把 CPU 当作 GPU |
| `--backend cpu` | OpenCV CPU；播放保持原速，但分析频率与延迟较差 |
| `--playback offline` / 默认 `--headless` | 逐个采样帧完整分析，便于可重复回归；不保证按源速度播放 |
| `--save-video` | 实时模式导出组合画面录像；离线模式导出同帧分析回放 |

实时模式默认目标分析 8 Hz，离线默认 5 Hz，可用 `--sample-fps` 调整。目标频率不是已完成推理频率，后台来不及时只处理最新帧；日志记录实际完成数。8 Hz 的 GUI 实测显示约 28.55 fps、平均分析 100.86 ms、平均结果年龄 171.96 ms。另一段红转绿的 20 秒原速 GUI 测试显示约 29.46 fps、平均分析 101.78 ms。

DirectML 已安装到现有 Python 3.11 环境，版本 1.24.4。其他电脑缺失时可安装：

```powershell
py -3.11 -m pip install onnxruntime-directml
```

实时界面左侧是当前视频，右侧是最近完成分析的原始帧及其真实目标框、车道和灯色，下方显示对应分析帧的判断与延迟。旧检测框不直接叠到新视频帧。Space、A/D、K、S、R、T 和退出按键仍可使用。

分析结果落后超过 750 ms 时，显示待确认、将显示决策权限改为未知。变道请求使用落后最多 500 ms 的结果，超出时立即回应无法判断；暂停后视频时间冻结，可使用暂停画面的有效分析结果。旧会话的在途分析完成后不会显示到重播会话中。

实时分析输出可能跳过中间帧。平滑显示只代表播放正常，不证明每帧都被识别，也不证明违规事件没有遗漏。当前是 Windows 性能优化与规则验证，不是实际车辆控制。

## 3. 实测

同一个 4.60 秒源画面，预热后的双模型推理及预后处理：CPU 约 349 ms，DirectML 约 48 ms。实际工程还包括边界拟合、原图线型、灯色/形状、轨迹、道路上下文与决策，所以不能用这 48 ms 当作整条链路耗时。

三个视频保持 640×640 模型输入、相同采样与配置，完整离线分析共 677 帧：

| 视频后缀 | CPU 基线平均分析 | GPU 平均分析 | 主动作逐帧一致 |
| --- | ---: | ---: | ---: |
| `112507` | 409.60 ms | 100.49 ms | 225 / 225 |
| `113421` | 386.39 ms | 85.45 ms | 66 / 66 |
| `113539` | 390.69 ms | 97.23 ms | 386 / 386 |

此计时不包含后续绘制、编码与日志。GPU 和 CPU 可能有轻微浮点、框坐标与置信度差异；主动作一致不等于检测完全一致，也不是识别准确率。真实误报关键帧和第三段红转绿仍保持预期主动作。

| 实时测试 | 显示 | 分析/限制 |
| --- | --- | --- |
| GPU，第二视频 8 秒，含 GUI 与录像 | 约 27.97 fps | 平均分析 112.15 ms；默认 5 Hz 测试平均结果年龄 225.34 ms |
| GPU，第一视频 8 秒，无窗口 | 约 29.31 fps | 40 个分析帧；平均分析 140.77 ms；结果年龄 237.42 ms |
| CPU 回退，第一视频 6 秒 | 约 29.32 fps | 仅分析 14 帧，16 个待分析帧被更新；平均年龄约 786 ms，不能作为低延迟识别验收 |
| 真实 GUI 自动按键 | 约 29.95 fps | 暂停后 A/D 立即回应，S 分别保存；R 重播生成新会话 |

耗时随其他进程、功耗和绘制/录像负载变化。GPU 全段输出目录为 `video_decision_runs/gpu_verified_112507/`、`gpu_verified_113421/`、`gpu_verified_113539/`；其他测试目录为 `realtime_gpu_gui_8s/`、`realtime_cpu_6s/`、`realtime_gui_keys/`。`summary.json` 明确记录后端、源帧率、分析帧数、显示帧数、显示 FPS、结果年龄和待处理帧替换数。

回归命令：`py -3.11 verify_video_behavior.py`（28 项规则）与 `py -3.11 verify_video_realtime.py`（12 项队列、重播、请求新鲜度及后端回退检查）。这些检查验证具体实现行为，不能证明比赛任务已经全部满足。

## 4. 模型契约更正

官方 YOLOv5 ONNX 用 ONNX Runtime 实际读出的输入、输出均为 FP16。此前旁侧清单写 FP32，只反映了 OpenCV 所接收的输入 blob，表述不准确，现已更正：

| 模型 | 文件实际精度 | 当前处理 |
| --- | --- | --- |
| YOLOv5s | FP16 输入与输出，无本地 INT8 量化 | OpenCV 输入 blob 使用 FP32；DirectML 根据模型声明转 FP16，解码时转 FP32 |
| YOLOP | FP32 输入与输出，无本地 INT8 量化 | 原 RGB/归一化与分割解码保持一致 |

模型权重和 SHA256 未改变，类别顺序、输出布局和预处理分别保存在 `models/yolov5s.onnx.json`、`models/yolop-640-640.onnx.json`。每轮结果记录实际推理后端；不能把 FP16 模型精度叫作已经完成 RK3568 INT8 量化。

## 5. 与题目要求的关系

| 用户提供的要求 | 当前情况 | 仍需完成 |
| --- | --- | --- |
| 指定视频的红停绿行、黄灯强闯报警 | Windows 已有灯色/方向原型和停车提示 | 黄灯强闯需实际运动/越停止线事件；当前视频状态机的 alarm_codes 仍为空，不能声称已实现 |
| 按键模拟左/直/右车道及停止/强闯 | A/D 当前用于变道请求；旧人工窗口可输入部分规则 | 比赛专用按键映射、车道模拟与实际行为/报警闭环尚未统一 |
| 虚线换道、实线直行、强制换道报警 | Windows 判断当前线型与单次变道条件 | 线型可靠性仍不足；实际跨线事件与当时线型快照、告警需完善 |
| 图像叠加/LED 提示 | Windows 有中文提示与对应分析帧叠加 | RK3568 决策输出到 FPGA、LED/HDMI 与报警验收尚未完成 |
| 带导航的道路视频与自主规划 | 地面方向/相机转向仅为估计 | 导航输入、路线/车道规划和执行反馈尚未完成 |
| MCU/ARM 上轻量模型实时识别 | 板端已有 COCO RKNN 目标检测；Windows GPU 加速已验证 | 新车道/信号方案需针对 RK3568 NPU 转换、量化、适配与性能验收 |
| 至少四路并行采集与低延迟 | 当前链路主要单路 | 四路同步、FPGA/PCIe 带宽、多路调度及端到端延迟验收尚未完成 |
| 夜间/复杂路口/避障 | 当前仅三个日间视频回归 | 专用场景数据、路径/障碍物推理、规则和可靠性验收尚未完成 |

接下来的优先级是：先把基础题目对应的可观测事件和报警闭环做完整，同时提高车道线有效证据；再选择适合 RK3568 的轻量网络完成 NPU 性能测试；针对证实的精度缺口使用本地 BDD100K 配对标注与自采数据微调；最后扩展导航、复杂场景和四路。训练可以在 Windows GPU 上进行，模型部署及最终低延迟验收必须在实机链路上完成。

本轮修正解决了电脑端播放被 CPU 推理阻塞的问题。RK3568 的实时性、车道精度、完整交通规则及高阶任务依然需要各自验收，不能用更流畅的 Windows 视频代替。

最终默认设置的真实窗口验证：第三个视频 9～29 秒，8 Hz 目标分析，20 秒内完成 160 帧分析，显示约 28.03 fps、平均分析 88.57 ms、平均结果年龄 155.42 ms、最大年龄 266.67 ms，待处理队列无替换。红灯区间保持 STOP，绿灯确认后解除。证据为 `video_decision_runs/realtime_default_verified/summary.json`。

性能优化阶段的完整 GPU 离线回归目录为 `video_decision_runs/gpu_final_112507/`、`gpu_final_113421/`、`gpu_final_113539/`，检查命令为 `py -3.11 verify_video_outputs.py`，报告为 `video_decision_runs/gpu_acceptance.json`。车道时序修改后这些目录的源码指纹已经过期，不能拿旧日志冒充当前版本。

当前车道专项测试目录为 `video_decision_runs/lane_patch_112507/`、`lane_patch_113421/`、`lane_patch_113539/`。使用 `py -3.11 audit_lane_boundary_outputs.py` 检查当前源码指纹、完整采样数量和暂存不放行规则，报告为 `video_decision_runs/lane_boundary_audit.json`。该审计没有重新执行旧报告中的 GUI 按键/导出视频验收，也不是识别准确率测试。

最终批次仍完成 677 帧，三个视频平均分析分别为 118.64 / 81.63 / 103.70 ms；相比前一批 GPU 测试有负载变化，应按范围理解。25 项视频/GUI 输出检查通过，包含当前推理代码指纹、完整导出、行人误报样例、红灯保持与绿灯释放、暂停 A/D 和重播新会话。规则回归 28 项与调度回归 12 项也通过。
