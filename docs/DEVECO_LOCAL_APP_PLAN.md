# 将RK3568预览迁移到本地OpenHarmony应用

可行，但要区分板端算法与桌面预览。现有PCIe采集、RKNN推理及一部分规则已经在RK3568运行；Ubuntu的Python/OpenCV窗口、跟踪展示、2.5D与冻结预演还需要迁移。DevEco Studio是开发工具，HAP打包不能自动将桌面Python界面变成ArkUI界面。

| 当前部分 | 本地化方案 | 复用程度 |
| --- | --- | --- |
| FPGA三路输入与PCIe驱动 | 保留驱动及采集链路，以设备权限受控的Native服务读设备 | 主要复用；需要检查驱动与系统镜像匹配 |
| RKNN模型/解码器 | C/C++ Native推理服务，使用对应RKNN运行库和模型合同 | 权重可复用；ABI与运行库需要适配 |
| 规则状态与请求 | Native服务输出状态，ArkUI按钮/硬件键提交请求 | 大量C逻辑可复用；接口整理 |
| RGB565视频预览 | Native转换并通过XComponent/Surface或该系统支持的图形接口送显 | 重写显示接入，避免每帧将大数组转为ArkTS对象 |
| 深色面板 | ArkUI/ArkTS重建布局、按钮与状态 | 沿用现有视觉规范，不直接运行OpenCV桌面窗口 |
| 跟踪/2.5D/冻结预演 | 将Python状态与几何迁移为C++/ArkTS，Canvas绘制示意道路 | 要迁移并对照回放，保留“实时/保持/推测/快照”的区别 |
| FPGA按键 | 保留KEY1～4原功能，将方向事件交给同一Native控制服务 | 复用事件通道，避免多个应用竞争设备 |

推荐分层为“设备与算法服务 + 本地显示应用”。高权限服务负责PCIe/RKNN，普通界面只读视频/状态并发送请求。前期也可用本机TCP/Unix socket连接服务，避免第一步同时改采集、推理和界面。低量状态经NAPI/IPC进入ArkTS；视频走Native显示通道。

## 开工前必须核对的环境

| 核对项 | 对方案的影响 |
| --- | --- |
| 实际OpenHarmony版本/API及系统形态 | 标准系统且有图形栈/ArkUI，才可以直接规划ArkUI HAP；无图形的定制系统可能先要更换或扩展镜像 |
| RK物理显示输出与输入设备 | 需要屏幕真正接到RK3568可用的显示输出；Ubuntu预览窗口不会自动成为RK本地窗口 |
| DevEco SDK与板端API/签名 | 使用匹配的OpenHarmony SDK和设备签名，不能按任意商用HarmonyOS手机工程直接部署 |
| `/dev/pango_pcie_multivideo_*` 权限 | 当前终端通过root访问，普通HAP不能默认拥有相同权限；需Native系统服务或系统级权限配置 |
| libc与ABI | 当前部分程序经自带glibc loader启动；OpenHarmony Native通常使用其SDK/系统运行库，现有ELF不一定能直接放进HAP加载 |
| `librknnrt.so` 与NPU驱动 | 核对系统兼容的RKNN库及分配/设备权限，保留FP16、INT8及模型输出解释合同 |
| 内存及显示开销 | 2GB设备上避免多份1080p数组来回复制；本地化可能减少USB预览链路开销，但不会自动提高模型推理速度 |

以上信息本轮未从实机读取，因此现在可以确定迁移方向，不能承诺直接导入现有二进制即可安装运行。

## 建议实施次序

| 阶段 | 交付与验收 |
| --- | --- |
| 1：系统与显示验证 | DevEco建立匹配版本的空应用，RK本地屏显示深色静态页面，确认签名/安装/显示/输入可用 |
| 2：三路纯显示 | 复用纯传输服务，本机连接9002或Native IPC显示三路，不依赖Ubuntu；测本地FPS与端到端延迟 |
| 3：HDMI识别与请求 | 接入已有模型、状态、A/D变道与KEY5/6/7方向，验证识别和控制并行，界面不阻塞推理 |
| 4：2.5D与冻结推演 | 逐项迁移目标跟踪、平滑、短时保持、快照、行人预测示意，与当前固定回放核对 |
| 5：演示入口 | 两种模式选择、启动/停止、日志、设备缺失提示、自启动和异常恢复 |

完成后Ubuntu/HDC可退出日常预览链路，Windows仍可继续作为HDMI和以太网的外部视频源。若还希望连Windows播放器也不要，则另行实现板上本地媒体输入；这与本地预览界面是两个需求。
