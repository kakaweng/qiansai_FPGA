# 辅助驾驶优化与实施方案

> 2026-10-30范围更新：用户决定先做HDMI单路，暂缓P0跨路时间戳。当前实施P1按三个任务合并：①手动选择方向和对应灯后的红停绿行/黄灯等待/强行行驶报警；②路口左直右反馈和屏幕虚拟LED；③实线禁止变道、虚线请求反馈。已新增独立 `front_p1` 入口，具体运行与边界以 [FRONT_P1_RK3568.md](FRONT_P1_RK3568.md) 为准。下面的自动箭头方向、闪灯、物理LED、多路标定等仍是后续规划，不能视为本版已完成。黄灯等待不包含自动倒车，YOLO漏检不作为闪灯证据。

## 目标

围绕赛题中的红绿灯行为、实线变道报警、行人冲突处理、导航模拟和真实道路演示，建立一条可追溯的链路：

```text
视频输入 → 感知结果 → 场景状态 → 驾驶决策 → 中文面板/LED/蜂鸣器 → 日志与回放
```

当前车道 A1 只解决车道结果的短时跳变。辅助驾驶后续工作使用车道的 `decision_type` 和结果年龄，不直接把预览中的 `HOLD` 当作可变道证据。

## 当前基线

| 模块 | 当前状态 | 后续处理 |
|---|---|---|
| HDMI 前方车道 | RK3568 `scene_v4`，A1 已将保持时间调整为550ms | 继续使用，记录 `age/reset/reason` |
| 前方车辆、行人、交通灯 | RKNN YOLO，前方 HDMI 独立异步更新 | 增加灯方向、闪烁状态和行人冲突区 |

| RK3568 C 控制器 | `drive_assist.c` 已支持变道请求、实线阻断、模拟车速/挡位 | 补齐信号方向、闪灯、行人和输出事件 |
| FPGA 输出 | 视频链路已通 | 增加 LED0/LED1/LED2、告警和事件序号映射 |

## 分阶段实施

### P0：统一观测协议和时间基准

先固定每帧决策输入，所有结果都带 `session_id`、`frame_seq`、`source_timestamp_ns`、`receive_monotonic_ns`、`fresh` 和 `age_ms`。感知模块只提供事实，决策模块只读取事实，不从旧画面推断新事件。

每帧建议使用以下结构：

```json
{
  "session_id": "waymo_scene_01",
  "frame_seq": 120,
  "timestamp_ns": 1234567890,
  "fresh": true,
  "signal": {
    "required": true,
    "bound": true,
    "state": "red",
    "direction": "straight",
    "flashing": false,
    "confidence": 0.91
  },
  "lane": {
    "state": "estimated",
    "left_boundary_type": "dashed",
    "right_boundary_type": "solid",
    "left_decision_type": "unknown",
    "right_decision_type": "solid",
    "age_ms": 180
  },
  "pedestrian": {
    "conflict": "clear",
    "track_id": 3,
    "time_to_conflict_ms": null
  },
  "request": {"maneuver": "keep_lane"},
  "actual": {"moving": true, "crossed_stop_line": false},
  "lane_change": {"event_seq": 0, "direction": "none"}
}
```

未知、过期、时间回退和输入间隔超过500ms统一进入 `WAIT` 类决策。`green` 只表示灯色事实，不自动等于左转、右转或直行许可。

### P1：路口信号和 LED/箭头闭环

这是最适合先完成的比赛演示功能，因为它不依赖侧方相机标定。

1. 对交通灯检测框增加方向分类：`left`、`straight`、`right`、`circle`、`unknown`。
2. 由场景配置绑定本车所在车道和信号方向；配置来源写入日志，不能只凭灯框位置猜测。
3. 对颜色和方向分别做连续确认，避免单帧误检改变动作。
4. 增加闪烁判定：至少观察两个亮灭周期；在周期尚未确认前保持 `WAIT_SIGNAL`。
5. 行为规则固定为：

| 信号 | 直行 | 左转/右转 |
|---|---|---|
| 红灯 | `RED_STOP` | `RED_STOP` |
| 红色闪烁 | `RED_FLASH_STOP` | `RED_FLASH_STOP` |
| 黄灯 | `YELLOW_WAIT` | `YELLOW_WAIT` |
| 黄色闪烁 | `YELLOW_FLASH_CAUTION`，减速等待 | `YELLOW_FLASH_CAUTION`，减速等待 |
| 绿色圆灯 | 仅在场景允许直行时进入确认 | 仍需对应箭头或转向许可 |
| 绿色左/右箭头 | 方向匹配后进入 `GREEN_ARROW_GO` | 仅允许对应方向 |
| 方向未知/信号过期 | `WAIT_SIGNAL` | `WAIT_SIGNAL` |

6. 输出映射暂定为：`LED0=左转`、`LED1=直行`、`LED2=右转`；红灯、未知和冲突时全部熄灭并输出告警码。

### P2：实线变道报警和虚线请求

沿用 A1 的车道边界结果，但把“显示类型”和“决策类型”分开：

- `SOLID`：对应侧变道请求立即输出 `SOLID_BLOCK`。
- `DASHED`：只解除线型限制，还要有邻道存在、邻道清空和结果新鲜证据。
- `HOLD`：预览可继续显示，决策类型必须是 `UNKNOWN`。
- `UNKNOWN` 或过期：输出 `LINE_UNKNOWN`，不允许放行。
- 实际跨线事件必须携带跨线前的边界类型、方向、事件序号和事件时间；事件只触发一次 `forced_solid_lane_change`。

P2 的演示画面同时显示“请求方向、边界类型、邻道证据、最终许可、拒绝原因”，避免把“检测到虚线”误解为已经确认安全。

### P3：行人冲突和模拟制动

不把检测到任意行人直接变成礼让。需要加入本车路径冲突判定：

1. 用车道走廊或人工配置的归一化 ROI 表示本车可能经过的区域。
2. 跟踪行人脚底中心、横向速度和进入方向。
3. 行人进入冲突区且连续确认3帧时进入 `YIELD_PEDESTRIAN`；预测将进入冲突区时进入 `PEDESTRIAN_CAUTION`。
4. 模拟车辆正在行驶时，输出 `STOP` 或减速动作；车辆已停止后保持停车原因。
5. 行人离开冲突区连续确认3帧才解除；短时漏检不能立即恢复通行。
6. 记录冲突区来源、轨迹编号、确认帧数和解除原因，便于解释误报。

### P4：导航动作融合

导航只提供“期望动作”，不能覆盖感知安全约束。输入动作定义为：`keep_lane`、`turn_left`、`turn_right`、`change_left`、`change_right`。

优先级固定为：

```text
红灯/红闪 > 行人冲突 > 车道实线 > 信号方向不匹配 > 证据未知 > 导航动作 > 保持车道
```

导航要求左转但当前没有左箭头或转弯许可时输出 `WAIT_TURN`；导航要求变道但对应边界为实线时输出 `KEEP_LANE` 和实线报警。

### P5：RK3568 与 FPGA 输出闭环

Windows 先完成规则和回放，RK3568 再接入同一套观测字段。板端输出保持结构化：

```text
state, recommended_action, permissions, alarm_codes, event_seq, source_age_ms
```

FPGA 只消费动作和告警，不重新解释模型结果。建议映射：

| 决策 | LED/箭头 | 蜂鸣器 |
|---|---|---|
| `GREEN_GO` | LED1 或配置方向灯 | 关闭 |
| `GREEN_ARROW_GO` | 对应 LED0/LED2 | 关闭 |
| `YELLOW_WAIT`、`WAIT_SIGNAL` | 全部熄灭 | 间歇提示 |
| `RED_STOP`、`RED_FLASH_STOP` | 全部熄灭 | 连续或高优先级提示 |
| `SOLID_BLOCK` | 请求方向红色告警 | 短促提示 |
| `YIELD_PEDESTRIAN` | 全部熄灭 | 连续提示 |

所有输出都使用 `event_seq` 去重；输入过期时自动清除允许通行和方向指示。

## Waymo 回放适配

`F:\\waymo_data` 当前包含5视角视频，适合 Windows 回放和多路时序测试。当前三路工程建议先使用：

| 工程输入 | Waymo 视角 | 用途 |
|---|---|---|
| HDMI | `front.mp4` | 主车道、信号、前方行人和车辆 |
| 左辅助 | `side_left.mp4` | 邻道车辆观察 |
| 右辅助 | `side_right.mp4` | 邻道车辆观察 |

如果需要前方重叠视野，可将 `left.mp4/right.mp4` 作为侧方输入，但它们不等价于真实侧视相机。视频需要裁剪/缩放到当前三路协议，Windows 回放器以 `frame_timestamps.csv` 的源时间戳驱动，缺帧时保留上一帧，不插帧。

Waymo 的三个 decoded 场景约10fps、每段约20秒；第三个场景有两个约200ms间隔，专门用于测试 `input_gap`、结果过期和状态机复位。数据没有检测标注和相机内参，因此它能证明时序、吞吐和跨域表现，不能直接给出检测准确率或完成严格空间标定。

已完成一次前视 smoke test：第一场景前视视频分析25帧，使用 DirectML，平均处理约113.4ms；车辆、行人和交通灯框进入 Windows 入口，交通灯语义仍显示未知。这说明 Waymo 适配层可用，下一步要补的是多路时间驱动和场景标记。

## 验收场景

每个场景同时保存原始帧、感知 JSON、决策 JSON、面板/LED 输出和延迟统计。

| 场景 | 必须验证 | 主要指标 |
|---|---|---|
| 十字路口直行 | 红灯停、绿灯行、红闪停、黄闪等待 | 状态转换、方向绑定、告警去重 |
| 十字路口转弯 | 左/右箭头匹配，方向不匹配等待 | 箭头方向正确率、未知信号不放行 |
| 车道变更 | 虚线请求、实线请求、实际跨实线 | 实线报警、虚线仍检查邻道、事件序号 |
| 行人冲突 | 路边行人不误报，进入冲突区制动 | 误触发率、确认帧数、解除帧数 |
| 导航道路 | 导航动作与车道/信号冲突时等待 | 动作融合和原因可解释 |
| Waymo 第三场景 | 200ms间隔和短时缺帧 | reset、age、过期清理 |
| 强光/夜间/复杂路口 | 题目要求的环境变化 | FPS、p95延迟、未知状态是否安全收敛 |

建议初始验收门槛：规则回放全部通过；红灯、红闪和实线不误放行；任何关键证据过期后不输出 `GO`；板端决策 p95 结果年龄不超过750ms；预览刷新和决策日志能够用同一 `frame_seq` 对齐。感知准确率需要另建人工标注小集后再统计。

## 实施顺序

1. 在 Windows 中完成 P0 协议和 P1 信号/箭头/闪烁状态机，使用 Waymo 三场景回放验证。
2. 在现有 A1 基础上完成 P2 实线报警和请求反馈，保持 `scene_v4` 回退入口。
3. 加入 P3 行人冲突区和模拟制动，先用人工标记片段验证，再接真实模型。
4. 接入 P4 导航动作和统一中文面板，记录每次等待/停车/禁止原因。
5. 将稳定的观测和规则迁移到 RK3568 C 控制器，最后接 FPGA LED/箭头/蜂鸣器。
6. 运行 Waymo 和真实四类演示视频，按延迟、过期、误触发和状态转换结果决定是否训练新模型。

重新训练的触发条件是：原图中人眼清楚看到目标，且已经排除输入时序、结果过期、ROI/绑定和状态机问题后仍持续漏检。训练工作放在 Windows GPU，RKNN 转换和最终延迟必须在 RK3568 验收。
